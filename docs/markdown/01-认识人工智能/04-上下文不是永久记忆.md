# 上下文不是永久记忆

**模型能接着一段对话回答，通常是因为应用把前面的消息再次放进了当前上下文，不等于模型已经永久记住。**

你在聊天开头说“我想做一份火星主题海报”，后面又说“把标题改成红色”。如果新一轮只有后一句，模型还知道要改哪张海报吗？不一定。它要能参考“火星主题海报”这条旧信息，应用就得把相关内容一起提供。

## 上下文像此刻摆在桌面上的资料

模型预测下一个 Token 时，只能参考这一次实际收到的上下文。

可以把上下文想成一张工作桌。做火星海报时，桌面上可能放着任务要求、上一版草稿和经过核对的火星资料。模型这一次可以参考它们；没有放上桌的内容，它不会凭空读到。

应用可能把这些内容放进上下文：

- **系统消息：** 说明任务、回答方式和使用边界；
- **用户消息：** 你提出的问题和要求；
- **助手消息：** 应用保留下来的之前回答；
- **其他资料：** 检索到的文档、工具结果和当前任务记录。

到底是谁把资料放上“工作桌”？是外围应用。它按照模型需要的格式整理内容，再交给模型。所以，聊天界面上看到的气泡，不一定就是模型最后收到的原始格式。

## 不同消息承担不同作用

### 系统消息先说明规则

系统消息可以告诉模型“现在要完成什么任务”“回答要用什么语气”“有哪些工具和限制”。

放在系统消息里的这类任务说明，常被叫作 **System Prompt（系统提示词）**。它是应用在任务开始前给出的说明，不是模型天生拥有的性格。

### 用户消息提出目标

用户消息是你这一轮发出的内容。问题越清楚，模型越容易知道你真正需要什么。

“介绍一下恐龙”很宽泛；“用初一学生能理解的语言，用三段介绍霸王龙的生活年代、食物和体型”就具体得多。

### 助手消息和工具结果补充当前进度

保留下来的旧回答可以帮助模型延续对话。搜索结果、天气数据和文件内容，也可以由应用加入上下文，让模型根据新信息继续工作。

## 提示工程和上下文工程有什么不同

### 提示工程重点是把要求说清楚

你写下“做一张 A3 火星海报，用初一学生能理解的语言，包含三个事实框”，是在把目标、格式和限制说清楚。这是提示工程关注的问题。

它很重要，但一个长任务不会只有开头那一句提示。对话历史、检索资料、工具结果、用户偏好和当前进度都会不断变化。

### 上下文工程重点是管理变化中的信息

**Context Engineering（上下文工程）**关注的是另一件事：下一次调用模型前，应用要从多轮对话、火星资料和最新修改中选出什么？哪些旧版本或无关内容要删掉、压缩、隔离或暂时放在外面？

Microsoft 的《AI Agents for Beginners》给了一个很实用的判断问题：模型下一步拿到的是不是“太多信息、错误信息，或者漏掉了需要的信息”？

简单说，提示工程管“要求怎样说”，上下文工程管“下一步给模型看什么”。目标不是塞得越多越好，而是让模型拿到 **足够、相关、可信** 的信息。

## 指令会影响回答，但不是安全护墙

如果提示词里写着“绝对不要删除文件”，工具却仍然拥有删除整个文件夹的权限，这道限制可靠吗？不可靠。

系统消息和用户要求会影响后续 Token 的生成，但模型仍可能误解、遗漏或没有正确遵循指令。删除文件、付款、发布内容等重要限制，要由权限系统和控制程序真正拦住。

一句话：**指令能引导模型，权限才能限制动作。**

## 上下文窗口有容量限制

### 工作桌再大，也不是无限的

模型一次能处理的 Token 数量有上限，这个范围叫作上下文窗口。不同模型的容量不同，但都不是无限空间。

对话、文件和工具结果不断加入，上下文会越来越满。

### 内容太多时，应用必须处理

常见做法包括：

- 删除较早或不再相关的消息；
- 只保留和当前任务最有关的资料；
- 把较早内容压缩成一段摘要，这常叫作上下文压缩（Compaction）；
- 把大任务拆成几个更聚焦的小任务。

摘要可以保留“火星主题”，也可能丢掉“标题必须是红色”这类细节。而且，模型不一定要等窗口完全装满才受影响；大量无关信息也可能分散它对当前任务的注意。

所以，长对话里的“忘记”，可能是旧细节没有继续进入上下文，也可能是模型没有正确利用已有内容。它不等于模型像人一样主动遗忘。

## 训练、上下文和记忆是三件事

| 名称 | 它是什么 | 换一段对话后还能直接使用吗 |
| --- | --- | --- |
| 训练得到的能力 | 训练时进入模型参数的语言和任务模式 | 通常可以，同一个模型仍有这些一般能力；但它不会因此知道刚发生的新事情 |
| 当前上下文 | 这一次请求里提供给模型的消息和资料 | 通常不可以，应用需要重新提供 |
| 应用保存的记录 | 外围程序保存的偏好、摘要或任务记录 | 只有应用再次取出并放回上下文时才可以 |

不同产品对“工作记忆、短期记忆、长期记忆”的叫法不完全一致。下面用这三个词区分几种应用设计，不表示模型内部真的有三套像人脑一样的记忆器官。

### 工作记忆：当前任务的草稿纸

工作记忆保存眼前这项任务最需要的信息，例如目标、已经确认的事实、刚得到的工具结果和下一步清单。

它不一定等于整段聊天记录，更像从许多材料中整理出来的一张任务便签。

### 短期记忆：维持一次会话

在同一段对话里，你先问“去巴黎的机票大约多少钱”，接着问“那里的住宿呢”，应用保留的短期信息能帮助模型知道“那里”指巴黎。

结束会话或重新开始后，这些信息不一定继续存在。

### 长期记忆：由外围应用跨会话保存

应用可以把经过选择的偏好、摘要或任务记录保存到数据库或其他存储中，下次需要时再检索并放回上下文。

真正的记忆管理不只是“保存”，还包括选择、检索、更新和删除。保存错误信息、保存过多隐私，都会带来新问题。

### 上下文不等于永久记忆

开启新对话时，应用通常会建立新的上下文。旧对话里的信息不会天然出现在新对话中。

有些应用会保存你的偏好或任务摘要，下次再把相关内容放进上下文。这是外围应用实现的记忆功能，不是模型天然、永久地记住了你。

## 上下文也会出错

### 无关信息会让模型分心

你和旅行助手聊了很久以前的一次露营，最后才问“帮我找下个月去上海的便宜车票”。下一次请求该留下什么？当前日期、目的地和票价要求显然更重要。如果系统把大量旧细节全部塞进上下文，模型可能反复讨论帐篷和装备，却忽略眼前任务。

这类问题可以通过筛选和摘要来减少。

### 新旧要求可能冲突

你先说“只看经济舱”，后来改成“这次看商务舱”。如果两条要求都原样保留，系统可能不知道该听哪一条。

更好的做法是明确记录：新要求已经覆盖旧要求，并让后续步骤只使用当前有效的版本。

### 错误信息可能在多轮任务里越滚越大

如果模型错误地写下“某个小机场有直飞国际航班”，系统又把它保存成任务事实，Agent 后面可能反复寻找根本不存在的机票。问题不是“记住得够不够多”，而是错误在被保存前有没有核验。

错误内容如果被保存，又在后续步骤中反复放回上下文，就可能持续影响任务。在部分 Agent 安全资料中，这类问题被称为 **Context Poisoning（上下文污染）**；这个术语的使用范围并不完全统一。重点是：重要信息进入任务记录或长期记忆前，先用可靠来源核验。

## 本课小结

- 上下文是模型这一次生成时能参考的消息和资料。
- 系统、用户、助手消息以及工具结果，可以承担不同作用。
- 上下文窗口容量有限，旧内容可能被删除、筛选或压缩。
- 上下文工程的目标是为下一步准备正确的信息，不是盲目塞入更多内容。
- 工作记忆、会话内的短期记忆和跨会话的长期记录由外围系统管理。
- 应用保存的长期记录，只有被重新放进上下文时才能影响回答；错误记忆同样会影响回答。
- 提示词可以引导模型，但高风险操作仍要靠真正的权限控制。
