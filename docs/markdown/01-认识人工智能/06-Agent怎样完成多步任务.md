# Agent 怎样完成多步任务

**Agent 不是一个会自己行动的“超级模型”，而是把模型、工具、任务记录和控制程序组织起来的系统。**

模型提出请求 → 控制程序检查并调用 → 工具执行并返回 → 控制程序记录结果并执行停止或确认规则。一次工具请求是 Agent 流程中可观察的一步，工具内部仍可能包含多个固定步骤。

## 先看一个完整任务

假设你说：

> 帮我整理一份周六去科学馆的参观计划。下午五点前回来，只查公开信息，不要替我订票。

系统可能要：

1. 找到科学馆官方网站；
2. 核对开放时间和预约要求；
3. 查询交通和预计用时；
4. 根据“下午五点前回来”调整安排；
5. 整理成一份带来源的计划。

如果官网突然显示“周六临时闭馆”，还要照原计划查路线吗？不应该。新结果已经改变任务，系统应先核对闭馆信息，再决定改日期、换场馆还是停止。

## 什么是 Agent

Agent 中文常译为“智能体”。这里说的不是有意识的电子人，而是一种围绕目标工作的 AI 系统。不同资料对 Agent 的定义不完全相同，本课抓住多步任务中最实用的部分。

> **Agent 通常把模型、当前任务记录、可用工具和控制程序组织在一起，根据中间结果连续完成多个步骤。**

在科学馆任务里，模型判断下一步查什么。网页和地图工具获取资料。任务记录保存开放时间、路线和限制。控制程序检查权限并拦住订票。

LLM 是其中的模型，Agent 是围绕任务搭起来的整个系统。把 Agent 简单理解成“更聪明的 LLM”，会漏掉这些关键部分。

## 先用三个问题看清 Agent

### 它在哪里工作

先用科学馆任务回答：它在浏览器、地图服务和当前任务页面中工作。更一般地说，Agent 总是处在某个环境中，例如聊天应用、文件夹、学习平台或旅行预订系统。环境决定了它可能接触到什么。

### 它能观察到什么

它能看到什么？科学馆官网内容、路线结果和报错都可以成为观察结果。更一般地说，网页文字、工具返回值、文件内容、任务状态和成功提示都可以成为观察结果。

它没有获得的传感器、接口或资料，就不能可靠地“看见”。

### 它能执行什么动作

它能执行什么？这个科学馆 Agent 只能查询和整理，没有订票权限。Agent 的动作范围取决于开发者实际开放的工具和权限。一个旅行 Agent 可以被允许搜索车次，但不一定能订票；可以读取日历，但不一定能修改日程。

这三个问题能拆掉“万能助手”的想象：**Agent 的能力永远受到环境、信息入口和行动出口的限制。**

## 一个 Agent 要组织哪些部分

### 目标与限制

目标说明最后要完成什么，限制说明哪些事情不能做。

“整理参观计划”是目标；“下午五点前回来、只查公开信息、不要订票”是限制。

### 模型

模型读取当前信息，判断下一步更适合查开放时间、算路程、整理计划，还是结束任务。

### 任务记录

任务记录保存已核对的开放时间、来源、工具结果和当前进度。它通常会被整理进上下文，帮助模型判断下一步。

### 工具

工具负责查询资料或执行被允许的动作。这个任务需要网页读取和地图工具，不需要订票工具。

### 控制程序

控制程序检查工具请求、参数和权限，处理报错，限制重试，并在完成、超限或需要人工确认时强制系统停止。

这五项是一张入门检查表，不是所有产品必须照抄的固定配方。

## 复杂任务要先拆开，但计划不能写死

### 先说清怎样算完成

“帮我安排一次出行”太宽泛。“整理一份周六科学馆计划，下午五点前回来，只查公开信息”才有可以检查的完成标准。

目标越清楚，模型、工具和人越容易判断任务有没有走偏。

### 再拆成可以检查的小任务

查开放时间、看预约要求、算交通时间、整理计划，分别需要不同信息，也有各自的完成结果。先问一句：如果官网说临时闭馆，哪些步骤还有效？已找到的官方来源仍有效，原来的路线和时间安排则要暂停。

任务清单最好写清：这一步要得到什么、需要哪个工具、结果交给后面哪一步。这样出错时可以只修受影响的部分，不必把整件事从头再做。

### 新结果出现后，只改受影响的部分

计划不是一开始写完就永远不变。科学馆临时闭馆、路线时间过长，或者用户把返程时间改成四点，都可能触发重新规划。

好的重新规划会保留仍然有效的信息，只调整受影响的步骤。Microsoft 的规划课程把这称为 Iterative Planning（迭代规划）。

## 核心循环：观察—判断—行动—检查

### 观察

读取目标、当前进度和上一步结果。例如，官网返回了两条日期不同的开放通知。报错、空结果和权限不足也属于观察到的新信息。

### 判断

根据现有信息，选择一个可检查的下一步。面对两条通知，可以先比较发布日期和生效日期，暂时不查路线。用户需要看到可检查的计划、依据和结果，不需要模型逐字展示隐藏的内部推理文字。

### 行动

需要工具时，模型提出调用请求，控制程序检查和调度，工具才执行。不需要工具时，模型也可以整理答案或提出结束任务。

### 检查

看新通知是否解决了冲突，结果是否可信、是否离目标更近、有没有违反限制。如果官方页面仍然互相冲突，就应该报告不确定并停下，不能替用户随意选一条。

相近的循环也常用“判断—行动—观察”来描述。有些教程会介绍 **ReAct（Reasoning + Acting）**，强调判断、行动和观察交替进行。它和这里的四步检查表有关，但不必把两者当成完全相同的固定流程。重点仍是 **根据真实结果调整下一步**。

### 检查不是一句“我检查过了”

可靠的检查要有外部标准：把结果和目标、限制、工具状态、可靠来源或测试结果逐项比较。

如果第一次方案不合格，就换方法、补资料或停下来请求帮助。让同一个模型把原答案再说一遍，不算独立验证，也不能证明错误已经消失。

## 跟着科学馆任务走两轮

### 第一轮：核对开放信息

系统先查询官网。如果看到“正常开放”和“临时闭馆”两条冲突信息，应该比较什么？先看发布日期和适用日期。如果官方页面仍然无法互相印证，就报告不确定并停下，不能挑一条顺眼的直接使用。

### 第二轮：调整路线

确认开放后，系统查询路线。假如返回结果显示单程要 70 分钟，原计划还能保证下午五点前回来吗？系统要用这条限制重新安排出发和返程时间。

如果接下来进入预约页面，需要姓名和手机号，系统必须遵守“不要替我订票”的限制，给出入口和注意事项后停止。

## Agent 必须知道什么时候停

一个可控的 Agent 至少要有这些出口：

- 任务已经完成；
- 连续报错，继续尝试没有意义；
- 达到步数、时间或费用上限；
- 缺少完成任务的关键信息；
- 下一步风险较高，需要人确认；
- 用户要求暂停或停止。

多步任务里，前面一个小错误可能让后面越走越偏。模型可以提出“应该停止”，但步数、时间、费用、重试次数和高风险动作的硬上限，应由控制程序强制执行。停止条件不是妨碍 Agent 工作，而是保证它还能被人控制。

实际限制要尽量能数出来。例如，某个具体系统可以设定“最多 12 步、同一工具最多重试 2 次、最多运行 5 分钟”。这些数字只是写法示例，不是适用于所有任务的通用安全值。如果网页状态含糊、按钮作用看不懂，也应该停止，而不是继续乱点。

## Agent 和固定工作流各有用处

批量计算总分、查询可能临时变化的参观信息、付款审批，哪些更需要固定路线？批量计算和付款审批更需要明确、可预测的规则；参观信息查询则可以允许 Agent 根据新结果调整。

固定工作流的主要路线由开发者提前写好，行为更容易预测。Agent 可以根据中间结果灵活选择下一步，但不确定性也更高。

Agent 更适合步骤无法完全预先写死、需要多次使用工具，并且必须根据新结果调整的任务。固定计算、明确审批流程和稳定的批量处理，通常更适合普通程序或工作流。

正如 Microsoft 入门课程提醒的：**能用 Agent，不等于每件事都应该用 Agent。**

真实产品常常把两者组合起来：

- 查资料和比较方案，可以让 Agent 灵活判断；
- 付款、保存和发布等关键步骤，交给固定规则和人工确认；
- 能用明确规则稳定完成的事，就没有必要增加不确定性。

还可以把“观察”和“行动”分开：先允许 Agent 搜索、阅读和整理候选；一旦要提交表单、发送消息、订票、付款或删除内容，就暂停并把具体动作交给人确认。

## 这些拓展词先认识

- **RAG（检索增强生成）：** 先检索外部资料，再把相关片段放进上下文辅助回答。
- **长期记忆：** 外围应用保存经过选择的偏好、摘要或任务记录，需要时再提供给模型。
- **Skills（技能）：** 在一些产品中，指可以重复使用的任务说明、资源和脚本组合。
- **MCP：** 帮助 AI 应用按共同方式连接工具和资料。

这四个词先认识名称就够了。它们都是可选的应用设计，不是每个 Agent 必须全部拥有的“四件套”；缺少其中某一项，系统仍然可能是 Agent。

## 本课小结

- LLM 是模型，Agent 是围绕目标组织起来的整个系统。
- Agent 会根据中间结果反复观察、判断、行动和检查。
- 复杂目标要拆成可检查的小任务，新结果出现时进行局部重规划。
- 工具负责执行动作，控制程序负责权限、错误处理和停止规则。
- Agent 更灵活，但不一定比固定工作流更适合所有任务。
- 任务完成、连续失败、达到上限或遇到高风险动作时，Agent 应该停止。
