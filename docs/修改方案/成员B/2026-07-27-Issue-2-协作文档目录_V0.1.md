## 1. 问题

扁平的修改日志和混在共同方案目录中的个人提案会产生三个风险：

1. 两人可能同时编辑同一记录，导致冲突或覆盖。
2. 个人提案合并到 `main` 后，可能被误认为已经修改共同主方案。
3. 审核者可能直接改写提案人的文件，失去清楚的作者和责任边界。

## 2. 共同主方案

以下文件保持原位置，不建立成员副本：

- `docs/方案/AI基础教育公益网站搭建方案_V0.2.docx`
- `docs/协作原则/项目协作/两人协作与分阶段部署方案_V0.2.md`

`main` 中已合并的版本是当前权威来源。修改时使用独立 Issue 和共享方案 PR，同一时间指定一名编辑者，另一名成员必须审核。

## 3. 个人目录

```text
docs/
├── 修改方案/
│   ├── 成员A/
│   └── 成员B/
└── 修改日志/
    ├── 成员A/
    └── 成员B/
```

- 成员 A 只直接编辑两个 `成员A/` 目录。
- 成员 B 只直接编辑两个 `成员B/` 目录。
- 审核意见写在 Issue 或 PR 中，由文件所有者修改。
- 成员 A/B 是固定协作者标识，不因职责调整而交换。
- 该人员目录例外只适用于这两个文档命名空间，不扩展到源码、内容、数据或测试。

## 4. 文件性质

修改方案记录拟议目标、影响、边界和验收。个人方案即使合并到 `main`，也不会自动覆盖共同主方案或公共契约。

修改日志记录已经实际完成的文件、验证结果和与原方案的偏差。日志不能把未批准提案写成既成事实。

## 5. 命名

- 修改方案：`YYYY-MM-DD-Issue-编号-主题_V版本.md`
- 修改日志：`YYYY-MM-DD-Issue-编号-主题.md`

禁止使用“最终版”“最新版”“new”“copy”等无法稳定追踪的名称。

## 6. 迁移

- Issue #1 尚未合并，其产品信息架构移动到成员 B 的修改方案目录。
- Issue #1 尚未合并的日志移动到成员 B 的修改日志目录。
- 已经进入共同主方案的内容不复制到个人目录。
- 后续若个人提案改变主方案语义，另开共享方案 PR 同步，不在个人目录中静默宣告生效。
